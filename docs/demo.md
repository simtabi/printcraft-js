# Demo

Three ways to run the demo sheet, and how its assets are built.

The demo is a working test sheet: twenty-three job tickets, each printing the same
sample content through a different pipeline, plus the interaction layer and the
devtools controls. It is also the fixture the browser test suite drives.

## What it covers

Seven sheets, each exercising a different part of the library:

| Section                     | What to try                                                                |
| --------------------------- | -------------------------------------------------------------------------- |
| Quarterly production report | the print target every other section aims at                               |
| Field memo                  | invented PII, for the redaction and privacy jobs to censor                 |
| Declarative triggers        | buttons carrying their whole job in `data-printcraft-*`                    |
| Interaction layer           | the right-click menu, the palette, and every keybinding                    |
| **The proof sheet**         | the assembled document before it prints, annotation, and the colour picker |
| Two interfaces, one page    | two scoped menus that do not know about each other                         |
| Backends · Devtools         | the handoff seam, and the job record                                       |

The proof section is the one to start with: **Proof the whole page** paginates
everything into real numbered sheets with a cover and a notes page, and its
Annotate button draws on them with a pen that thins as it speeds up.

## Where to run it

|                |                                                                                                                                              |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **Hosted**     | <https://simtabi.github.io/printcraft-js/> — nothing to install                                                                              |
| **Standalone** | [`standalone.html`](https://simtabi.github.io/printcraft-js/standalone.html) — save it and open from `file://`; works with no network at all |
| **Local**      | `npm run build && npm run demo`                                                                                                              |

## No inline code

`demo/index.html` is markup and nothing else: no `<style>` block, no `style`
attribute, no script body. Behaviour lives in `assets/js/demo.js`, styling in
`assets/scss/` and `assets/css/`, and a packaging test fails the build if any of
it creeps back into the HTML.

The demo script is a **classic script, not an ES module**, on purpose: the
standalone build has to run from `file://`, where module scripts are blocked by
CORS.

## Asset layout

Sources live under `demo/assets/`, grouped by kind:

```
demo/
├── index.html                 markup only
└── assets/
    ├── scss/                  the component layer
    │   ├── _tokens.scss       palette, type stacks, crop-mark geometry
    │   ├── _mixins.scss       crop ticks, focus ring, label voice, page column
    │   ├── _controls.scss     buttons and the process-ink rules
    │   ├── _sheet.scss        page furniture and the sample sheets
    │   ├── _tickets.scss      job-ticket cards
    │   └── main.scss          the entry that pulls them together
    ├── css/tailwind.css       the Tailwind v4 entry: @source and @theme
    ├── js/demo.js             every behaviour on the page
    ├── img/watermark.svg      the sample image watermark
    ├── favicon/               .ico, .svg, apple-touch, 192/512 PNGs, manifest
    └── data/printcraft.config.json   page-wide defaults
```

The build writes the compiled equivalents to `dist/assets/`, mirroring the same
shape, and `demo/index.html` points at those.

## Two style layers

Sass owns the components; Tailwind owns the utilities and the design tokens the
markup reaches for. They are compiled separately and concatenated, because
`@import "tailwindcss"` cannot be fed through Sass, which resolves bare imports as
Sass files.

```
assets/css/tailwind.css   ──tailwindcss──┐
                                          ├──► dist/assets/css/demo.css
assets/scss/main.scss     ──sass─────────┘
```

Sass output goes **second**, so its unlayered component rules win over Tailwind's
layered utilities on equal specificity. That is deliberate: a component class is a
decision, a utility is a default.

The palette is defined twice by necessity, as Sass variables in `_tokens.scss`
and as custom properties in the Tailwind `@theme` block, because each tool needs
it in its own syntax. Keep the two in step; the values are the same.

## The favicon

`assets/favicon/favicon.svg` is the source of truth. The raster sizes are
generated by `npm run favicons`, which draws the mark directly in pixel space
rather than rasterising the SVG, which would mean pulling in a browser engine to
render four rectangles. The output is committed, because a favicon is a static
asset rather than a build product. If you change the mark, change both.

The standalone build inlines the SVG as a `data:` URI, so even the icon costs no
request.

## The standalone build

`tools/build.mjs` replaces every marker pair in `demo/index.html` with an inlined
equivalent:

| Marker              | Repo demo                      | Standalone                  |
| ------------------- | ------------------------------ | --------------------------- |
| `PRINTCRAFT:ICON`   | four `<link>` tags             | one `data:` URI             |
| `PRINTCRAFT:CSS`    | `<link>` to `demo.css`         | a `<style>` block           |
| `PRINTCRAFT:CONFIG` | empty                          | an inline JSON config block |
| `PRINTCRAFT:LIB`    | `<script src>` + `data-config` | the bundle inlined          |
| `PRINTCRAFT:DEMO`   | `<script src>`                 | the demo script inlined     |

The config is the interesting one: the repo demo fetches it through the script
tag's `data-config`, and the standalone switches to the inline-JSON form, because
a `file://` page cannot fetch a sibling file. Both are documented library
features. See [Configuration](configuration.md).

The generator refuses to inline any asset containing a literal `</script>`, and
refuses to emit a page that still references a file. A test then re-checks the
result independently.

## Sample data is deterministic

The run log and the chart are drawn from a seeded generator rather than
`Math.random()`. The demo doubles as a visual test sheet, so two screenshots of it
have to be comparable.

The memo section contains invented PII: an email, a phone number, an SSN and a
card number, so the redaction and privacy jobs have something to censor. Every
identifier in it is fake.
